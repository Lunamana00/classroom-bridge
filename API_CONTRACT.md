# Prototype contract

All UI text Korean; product name **KHU조교 / KHUsistant**. Local prototype with a real SQLite store, MCP transports, and FactChat gateway evidence selection through the official OpenAI SDK. No generated LLM answers claimed: display source excerpts and a copyable grounded-answer prompt for the external LLM. Course-scoped data. Google OIDC web login and course-scoped memberships protect the web API. HTTP MCP uses OAuth; stdio is unsupported.

Provider selection from server environment, read on startup:
- `CLASSROOM_MODE=auto` (default): nonempty `OPEN_API_KEY` (or `OPENAI_API_KEY`) selects codex mode; otherwise lexical demo.
- `CLASSROOM_MODE=codex`: OpenAI Responses API with `CODEX_MODEL=gpt-6-luna`.
- `CLASSROOM_MODE=jev`: FactChat Decisions API with `JEV_MODEL=jev-1.14.0`; SDK `post("/decisions/", cast_to=dict, body=...)` uses the gateway state/questions (noul) schema. No direct TypeSafe calls.
- `CLASSROOM_MODE=demo`: lexical retrieval, with no question-judgment API calls. Concept extraction also stays off unless explicitly enabled with `CONCEPT_EXTRACTION_MODE=api`.
- `CLASSROOM_RETRIEVAL=concepts` (default) selects GPT evaluation of all approved, source-available course concepts for codex and keyed auto mode. `CLASSROOM_RETRIEVAL=lexical` explicitly retains legacy word-based candidate retrieval. Jev and demo always retain the lexical path; no silent fallback is performed.
- Explicit API modes require a key. Failures are surfaced without fallback. Both modes use official OpenAI Python SDK with configurable `OPENAI_BASE_URL` (default `https://factchat-cloud.mindlogic.ai/v1/gateway`) and `max_retries=0`.
- GPT uses `responses.create`, `store=false`, no tools, and strict JSON Schema, with ID and score validation. Jev uses `/decisions/`, bounds concurrency to two, filters relevance/evidence/injection scores, preserves source text, selects up to three passages, then checks combined sufficiency. Jev's ranking score is a heuristic, not a calibrated correctness probability. The Responses-only `store` parameter is not sent to Jev.
- Entrypoints load environment in this precedence: process variables, `.env.local`, `.env`. Both files are gitignored. `OPEN_API_KEY` takes precedence over the standard alias.
- `CONCEPT_EXTRACTION_MODE=auto|api|disabled` (default auto) prepares drafts separately from question requests. auto requires a key and non-demo classroom mode; api explicitly permits extraction in demo; disabled makes no extraction calls. `CONCEPT_MODEL` falls back to CODEX_MODEL then gpt-6-luna. It uses the same gateway/key, strict Responses JSON Schema, no tools, store=false, bounded source batches covering all chunks and a bounded approved-concept context (oversized context fails explicitly). Source and merge-target IDs are validated. Model outputs are drafts, never human approvals. Only subsequent teacher approval makes source-backed concepts eligible for default concept retrieval.
- GPT all-concept retrieval sends the student question, every approved source-available concept in the course (name, description, aliases, revision and source IDs), and their deduplicated original source excerpts in one Responses call. There is no lexical or embedding prefilter and no arbitrary three-concept cap. It validates selected concept/source IDs and scores, preserves original source text, and checks sufficiency. Selection can be empty. Concept relevance is not a calibrated correctness probability or validation of a mathematical/engineering solution. If there are no eligible approved concepts, return an explicit preparation notice, empty concepts/evidence and sufficient=false without an API call. Oversized input fails explicitly rather than truncating the catalog or raw sources. Provider failure does not trigger lexical retrieval.

Errors JSON {detail:string}. No authentication credentials in browser config, error responses, or application logs. Source contents are escaped untrusted text.

Provider configuration comes from environment variables; `.env.local` and `.env` are loaded only by entrypoints.

Teaching/exam prompt context includes `material_catalog:[{id,title,filename,chunk_count}]` for every registered material and `source_scope:{total_materials,included_materials,total_chunks,included_chunks,priority_chunks,truncated,notice}`. Up to 60 source excerpts are included. At 60 or fewer chunks the original material/chunk order is preserved. For larger courses, up to 12 still-live evidence IDs from the recent eight questions and draft/published quizzes are prioritized, followed by one passage per PDF where capacity permits, then excerpts spread across other materials; remaining capacity is filled in rounds. The catalog describes registration coverage and is not evidence for facts absent from the selected excerpts. Scope limitations remain explicit, and course-level aggregates are not date-filtered reports.

Instructor tools: list_courses(), get_question_insights(course_id), get_teaching_brief(course_id), prepare_exam_plan(course_id,total_questions), add_course_material(course_id,title,text), propose_concept_quiz(course_id,title,concepts,question,kind,correct_answer,explanation,source_chunk_ids,options?,accepted_answers?), list_concept_quizzes(course_id), review_concept_quiz(course_id,quiz_id), publish_concept_quiz(course_id,quiz_id,review_token,confirmation), get_quiz_insights(course_id). propose_concept_quiz returns a private draft with review_url and approval_required=true; list_concept_quizzes returns {quizzes:[PrivateQuiz]}. The instructor may approve through the MCP review/confirmation flow or through the browser session/CSRF route. HTTP mounted /mcp/student and /mcp/instructor (no extra /mcp suffix). stdio is unsupported; use the HTTPS OAuth endpoints. The deployed HTTPS endpoints require OAuth bearer tokens and enforce course memberships.

Core-concept preprocessing and approval contract:
- Upload and direct-text registration queue a durable material job after saving original chunks. The background worker makes provider calls outside write transactions, claims jobs using leases, and stages results atomically. Jobs persist across restarts; normal cancellation requeues work and expired leases can be claimed again. Failures or missing configuration are explicit and require an extraction retry. Seeded/old materials can be queued manually; they are never silently processed on migration.
- Teacher GET /api/courses/{id}/concepts -> {concepts:[CourseConcept],jobs:[ConceptJob]}; GET .../concepts/{concept_id} -> CourseConcept. Students cannot access these endpoints, drafts, extraction state, or review mutations.
- Teacher POST /api/courses/{id}/materials/{material_id}/extract-concepts -> ConceptJob (202). Queues existing material or retries a completed/failed/unconfigured job; an already pending/processing job is reused. It never approves concepts. Removed/foreign material is unavailable.
- Teacher PUT /api/courses/{id}/concepts/{concept_id} accepts {expected_revision:int,name:string,description:string,aliases:[string],source_chunk_ids:[int],merge_target_id:int|null}. Only drafts may change. Limits: name 200 characters, description 4000, up to 40 aliases of 200 characters, 1..1000 source IDs. All sources and merge targets must belong to this course; merge targets must be available approved concepts. The server snapshots the target revision. Editing increments revision and never approves.
- Teacher POST .../concepts/{concept_id}/approve or /reject with {expected_revision:int} explicitly approves or excludes the reviewed draft. Current teacher membership, session, CSRF and exact draft revision are required. No MCP approval tool exists. The web review shows name/description/aliases/full source passages and requires a separate confirmation action.
- CourseConcept: {id,course_id,name,description,aliases,status:"draft"|"approved"|"rejected"|"merged",revision,merge_target_id,merge_target_revision,merge_target_name,source_chunk_ids,sources:[{chunk_id,material_id,title,text,page,section}],available,extraction_model,approved_by,approved_at,reviewed_by,reviewed_at,created_at,updated_at}. available means at least one source remains; it does not assert factual correctness. A removed source increments revision so stale approval fails. Approved concepts without sources remain visible for audit and cannot serve as merge targets.
- Duplicate names/aliases are normalized with Unicode NFKC, case folding and whitespace removal; meaningful symbols remain distinct (for example C, C++, C#). Matching unreviewed drafts combine aliases/evidence and increment revision; approved data receives a separate merge draft. The model additionally aligns names against existing drafts and earlier batches and suggests semantic matches against approved concepts. Identity descriptions are explicitly labeled as bounded excerpts; actual source chunks are never silently truncated. These are proposals that can miss duplicates or conflate related concepts; the professor reviews and edits them. No completeness guarantee is made.
- Approving a merge preserves the canonical approved name/definition, adds the reviewed draft's aliases/evidence, increments the canonical revision, and marks the proposal merged. A changed target requires saving/reviewing the draft again. Concurrent extraction never silently changes an approved concept. Retry results that contribute no new evidence/aliases are ignored.
- ConceptJob: {material_id,course_id,title,status:"pending"|"processing"|"ready"|"failed"|"not_configured",error,model,attempts,created_at,updated_at}. Provider diagnostic payloads, API keys and internal lease tokens are never returned. ready can legitimately contain zero proposals when no core teaching content is found.
- Instructor MCP list_course_concepts(course_id) returns the overview plus review_url; extract_material_concepts(course_id,material_id) queues the job plus review_url. Approval stays in the authenticated teacher web workspace. add_course_material also queues extraction. Existing and seeded materials require an explicit extraction request and subsequent approval before they contribute concepts to default retrieval. Student MCP tool names and quiz-selection/approval/grading rules remain compatible; search results additionally include selected approved concepts and retrieval metadata.

Approved concept quiz contract:
- Teacher GET /api/courses/{id}/quizzes -> {quizzes:[PrivateQuiz]}; POST the same route with QuizDraftInput -> PrivateQuiz (201).
- Teacher PUT /api/courses/{id}/quizzes/{quiz_id} with QuizDraftInput edits only a draft and increments revision. POST .../{quiz_id}/publish {expected_revision:int} records the approving teacher and publishes the reviewed draft only when its current revision matches the reviewed revision. Missing revision is 422; stale revision is 400 so another edit cannot silently change what is approved. POST .../{quiz_id}/archive stops delivery and grading. Both return PrivateQuiz. Published content is immutable; archived quizzes cannot be republished. Create a new draft for revised content.
- Instructor MCP review_concept_quiz returns PrivateQuiz plus review_token,expires_at (epoch),confirmation_phrase and approval_notice. The LLM displays the full question, rubric, sources and version to the professor and waits for explicit approval before calling publish_concept_quiz with that token and exact confirmation_phrase. A review token is bound to the reviewer, course, quiz and revision, expires after ten minutes and is consumed once on successful publication. Missing/invalid review, incorrect confirmation, stale revision, foreign reviewer, expiry or reuse cannot publish. The server verifies the authenticated teacher and review binding; the LLM must preserve the requirement for actual professor authorization, which a confirmation string alone does not independently prove. Web and MCP approval record approval_channel="web"|"mcp" for audit.
- Teacher GET /api/courses/{id}/quiz-insights -> QuizInsights. Member GET /api/courses/{id}/quiz-progress -> the authenticated user's QuizProgress; no target student parameter exists.
- Member POST /api/courses/{id}/quiz-answers {delivery_id:string,answer:string} -> QuizGrade. Unknown input fields such as student_id or is_correct are rejected (422). OAuth MCP tools obtain the actor from the bearer token and never accept an actor or correctness flag.
- QuizDraftInput: {title:string,concepts:[string] (1..8),question:string,kind:"multiple_choice"|"short_answer",options:[string]?,correct_answer:string,accepted_answers:[string]?,explanation:string,source_chunk_ids:[int] (1..8)}. All source chunks must exist in the same course. Multiple choice requires 2..6 distinct options, an A..F correct option ID, and no aliases. Short answer requires no options and permits up to 20 exact aliases. The server does not generate or semantically judge a rubric.
- PrivateQuiz includes id/quiz_id,course_id,status:"draft"|"published"|"archived",title,concepts,question,kind,options:[string],correct_answer,accepted_answers,explanation,source_chunk_ids,sources,available,revision,created_by,approved_by,created_at,updated_at,approved_at,approval_channel. Private source references include raw source text for teacher review.
- PublicQuizDelivery: {quiz_id:int,quiz_version:int,delivery_id:string,title,concepts,question,kind,options:[{id:string,text:string}],sources:[{chunk_id,material_id,title,page,section}],relevance:{method,score},is_preview:bool,expires_at:int}. No correct_answer, accepted_answers, explanation, or raw source text is added to the public quiz object. Ordinary search evidence remains available separately. Up to three published, source-available quizzes are selected by concept matching and linked source overlap. Relevance is a heuristic, not a correctness probability.
- Delivery IDs are opaque and bound to course, quiz revision, authenticated recipient and question, with a seven-day expiry. A teacher's delivery is marked preview. Expired, archived or missing-source quizzes cannot be delivered or graded. The student must explicitly answer; an unanswered/invalid answer is not recorded as incorrect.
- QuizGrade: {attempt_id:int,quiz_id:int,delivery_id,concepts,answer,is_correct:bool,correct_answer,explanation,grading_method:"choice_exact"|"normalized_exact_match",is_preview:bool,is_first_attempt:bool,recorded_at,replayed:bool,notice}. Correct answer and explanation are released to that recipient after a valid submission. MCQ accepts a displayed option ID, a valid one-based option number, or exact option text. Short answers match the teacher's correct answer or aliases after Unicode NFKC, casefold and whitespace normalization. This does not assess free-form semantic equivalence.
- A delivery accepts one raw answer. Repeating the same delivery and identical raw answer returns the same attempt with replayed=true; a changed answer is rejected. A new delivery permits a retake, retained in history. SQLite transactions make duplicate requests idempotent.
- QuizProgress: {attempt_count:int,first_attempt_count:int,retake_count:int,preview_attempt_count:int,concepts:[ConceptMetric],recent_attempts:[{attempt_id,quiz_id,title,answer,is_correct,grading_method,is_preview,is_first_attempt,recorded_at}],notice}. Student response metrics use only the first non-preview submission for each student and quiz; retries and teacher previews do not improve the estimate. The recent history is limited to 20 rows.
- ConceptMetric: {concept,first_attempt_count:int,correct_count:int,incorrect_count:int,accuracy:number|null,estimated_correctness:number|null,status:"insufficient_data"|"needs_review"|"developing"|"consistent_correct",quiz_count:int,student_count:int,method:"beta_1_1_first_attempt_response_ratio"}. accuracy = correct/count; estimated_correctness = (correct+1)/(count+2), rounded to four decimals, or null with no observations. Fewer than three first responses yields insufficient_data; otherwise observed accuracy below .6 is needs_review, below .8 developing, else consistent_correct.
- QuizInsights adds student_count,total_attempts,students:[{student_id,student_name,...QuizProgressWithoutRecentAttempts}],students_truncated to the aggregate progress fields. At most 500 students are expanded. QuizInsightsWithoutStudents omits students before insertion into teaching/exam prompts.
- These are response-based practice signals, not calibrated mastery, grades, or proof of unaided human performance. Responses forwarded by an LLM may include assistance. Preserve sample size, retakes, preview and insufficient-data notices in any teaching decision. A concept tagged to multiple quizzes contributes one first response per quiz; multiple tags share the same observation.
- Session and OAuth access checks apply on every operation. Students cannot list private quizzes, approve drafts, read class insights, submit another user's delivery, or query another user's progress. Domain permission errors map to 403, unavailable resources to 404, invalid domain inputs to 400, and schema errors to 422.

Verification scope: HTTP MCP SDK tests, browser callback verification, and explicit rejection of unsupported stdio; both gateway modes are tested using mocked SDK transports, including source preservation, validation, errors, credential isolation, and no fallback. Live evidence selection with the local key succeeded for gpt-6-luna via Responses and jev-1.14.0 via Decisions. ChatGPT/Gemini product integrations are not claimed as verified.

Web authentication:
- GET /api/auth/me is public and returns user summary, csrf_token, can_create_course, google_configured, mcp_oauth_ready=true.
- GET /auth/google and /auth/google/callback implement Google OIDC through Authlib (state/nonce/PKCE and ID-token validation).
- POST /auth/logout revokes the hashed server-side session and clears the HttpOnly cookie.
- All other /api/* endpoints require login. Mutations require X-CSRF-Token. Course operations enforce course membership; students may GET materials, POST ask, submit their own delivered quizzes and read their own quiz progress. All management, quiz approval and class analytics require the course teacher who is also in CLASSROOM_TEACHER_EMAILS.
- GET /api/courses returns only memberships, with role per course. POST assigns its creator as teacher.
- POST /api/courses/{id}/invite rotates a seven-day link; DELETE revokes it.
- POST /api/join {token} enrolls the authenticated user as student without changing an existing teacher role.
- GET /api/courses/{id}/members lists participants for the teacher. DELETE /api/courses/{id}/members/{user_id} removes a student and revokes existing invitations.
- Pre-auth courses are assigned to the first allowlisted teacher who logs in. Unknown Google users are students with no course access.
- HTTP MCP requires a bearer token independent of browser cookies; stdio exits without exposing tools.
- No production OAuth callback or Google account login is claimed verified before real client credentials and user interaction are supplied. Local permission tests use synthetic identities exclusively through internal test helpers.

MCP OAuth authorization:
- GET /.well-known/oauth-authorization-server advertises /authorize, /token, /register, /revoke and PKCE S256.
- GET /.well-known/oauth-protected-resource/mcp/{student|instructor} describes each resource and its required classroom:student or classroom:instructor scope.
- Anonymous MCP requests return 401 with WWW-Authenticate resource_metadata. Valid tokens with missing scope return 403. Tokens for another resource return 401.
- POST /register supports DCR with none, client_secret_post and client_secret_basic. HTTPS callbacks or HTTP loopback callbacks only; no fragments, credentials or wildcards. Client secrets are encrypted with a key derived from the server signing secret.
- GET/POST /authorize requires an exact supported resource and PKCE S256, then redirects to a ten-minute opaque /oauth/consent request. Anonymous browsers sign into Google and return to the same consent request.
- POST /oauth/consent requires a web session and CSRF form token. Approval creates a 120-second one-use code bound to user, client, redirect, scopes, resource and PKCE challenge. Denial returns access_denied with the original client state.
- POST /token requires the same resource on code exchange and refresh. Code redemption is atomic. Access tokens last one hour; refresh grants last at most 30 days, rotate on use, and reject scope expansion. Reusing a refresh token revokes the grant family.
- POST /revoke and DELETE /api/oauth/connections/{grant_id} revoke the whole token family. GET /api/oauth/connections lists only the signed-in user's connections; these API routes inherit session and CSRF controls.
- Access tokens, refresh tokens, authorization codes and consent tickets are stored as hashes. OAuth state and user/course data survive service restarts in SQLite. Tokens are never exposed in /api/config or the connections UI.
- The official MCP SDK handles core client/redirect/PKCE validation and bearer auth. Compatibility wrappers enforce RFC 8707 resource binding, advertise public clients, and normalize Basic client_id / nullable revocation fields for SDK 1.30.
- Bearer auth runs in the full SDK ASGI app; route extraction must not drop that middleware. Instructor membership and current teacher allowlist, or student course membership, are checked again inside every tool/prompt.

Browser origin policy:
- Same-origin checks apply to cookie-authenticated /api/* mutations and /auth/logout. /oauth/consent additionally rejects explicit foreign origins, while Origin:null is accepted only through the existing authenticated-session plus CSRF form-token check.
- /authorize, /register, /token and /revoke use OAuth validation instead of a web-page origin match. MCP endpoints use bearer tokens independently of web cookies.
- MCP SDK Host/DNS-rebinding checks remain enabled. Exact app, https://chatgpt.com and https://chat.openai.com origins are supported. Optional CLASSROOM_MCP_ALLOWED_ORIGINS adds exact browser origins, without wildcard matching.
- MCP CORS preflight and auth response headers are available for these origins; allow_credentials is false. Unknown origins do not receive CORS permission and authenticated MCP requests from them are rejected by SDK origin validation.

Consent redirect browser policy:
- The consent page CSP form-action permits self plus only the validated origin of the registered callback. Keeping self alone blocks external OAuth callback redirects in Chromium/WebKit even after the server issues the code.
- Callback origins are restricted to URL host/port characters before becoming CSP sources; path/query and directive delimiters are never interpolated into CSP.
- consent.js disables repeat submission while preserving the clicked allow/deny decision in form data. Authorization codes remain one-use; the consent TTL is unchanged.
- Browser verification uses an isolated local fixture: old self-only CSP blocks the first-click redirect, whereas the corrected policy reaches a distinct callback origin and exchanges the code on one click. HTTP client tests alone do not evaluate CSP.
